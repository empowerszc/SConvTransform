两条路径

编译器交付物，与性能上限探针

同一套算法有两种承载方式：一条必须留在 IR 里，一条可以激进地做运行时自适应。

交付路径

MLIR / ConvBench

交付物是 sconv-opt 一条命令。优化发生在 transform.structured.sconv、 packing lowering、-sconv-parallelize 与 OpenMP lowering 中；没有第二套运行时线程池。

成绩：单线程 33.3 ms / 127.7 GF（custom_0），多核 geomean 2.51×。

参考实现

native_impl

不受编译器抽象约束，用来回答“这个算法在 Kunpeng 上到底能跑多快”。它的数字是上限参考， 不直接算作交付路径的成绩。

成绩：18 用例 t1–t32 对 PyTorch geomean 1.51×–1.62×。

优化阶梯

每一步都先回答“钱花在哪”

从 ABI 时间、打包带宽、微内核粒度，到多核宽度与调度策略——顺序不是随意的。

里程碑与关键数字（2.0 GHz）
M1

快速输入打包

行分段 memcpy + 打包 buffer 上提复用。156.6 → 115.7 ms（−26%）， 其中约 28 ms 来自“不再每次落到冷页”。

M2

微内核 tile 放大

支持 multipacking，把 Nf 放大到 32。≈84–87 ms，未达 75 ms； 原因是打包后的 A/C 放不进 L2，端到端受 DRAM 限制。

A+C+G

边界拷贝与 tile 自适应

快 memrefCopy、宽 tile 下的 Nc 自适应、Nwin=160。 33.3 ms / 127.7 GF；单线程 geomean 1.57×。

M3

单 NUMA 多核

窗口 tile 循环 → scf.parallel → OpenMP + per-thread scratch。 geomean 2.36×，最高 338 GF；t16≈t32，宽度只有 5–20。

M4-c

多核专用 Nwin

多数形状降到 80/40，并用 CSA 探测阻止 IS→WS 翻转。 2.51× / 386 GF；宽度 40 不再更快，于是停手。

下一步

串行 / 带宽项

E1 filter 打包去 3/4 冗余 → E2 输入打包分段 → B 边界拷贝。 继续加宽（M4-a/b）按实测判据暂缓。

关键判断

三条最贵的经验

坑 1

归约维不能并行

把 Nc 标成并行，8/11 形状错、max_diff 1e6–1e8。它不是调度问题，是语义错误。

坑 2

“更多任务”不一定更快

Nwin 80 会让 c1/c2/9 翻到 WS、窗口组缩小；任务更多，时间反而 2 倍。tile 选择必须调度感知。

坑 3

微基准快 ≠ 端到端快

warm-cache 里 m16/n32/k108 只要 21 ms，in-situ 仍是 50–60 ms：A/C 放不进 L2。
