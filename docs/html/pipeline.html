管线 01

一条命令，从 linalg 到 OpenMP

所有优化都在 transform / pass 层完成；并行不是运行时偷偷开线程，而是 IR 里显式的 scf.parallel。

transform 与 pass 的顺序（M3/M4 共用同一条 lowering）
端到端命令bash
sconv-opt -transform=test/lowering/sconv-blas-fastp-mc.mlir \
  -sconv-parallelize -sconv-lower-parallel conv.mlir -o conv.mc.llvm.mlir
OMP_NUM_THREADS=16 numactl --cpunodebind=0 --membind=0 \
  mlir-cpu-runner conv.mc.llvm.mlir -e main -entry-point-result=void \
  -shared-libs=...,libomp.so

管线 03

IR 上看得见的变化

以输入打包为例：从逐元素 linalg.generic 变成一次运行时调用。

M1 之前：标量 gatherMLIR
scf.for %ic ...
  scf.for %fh ...
    scf.for %fw ...
      %v = tensor.extract %in[%n, %ic, %h, %w]
      tensor.insert %v into %pack[...]
M1 之后：行分段 helperMLIR
llvm.call @pack_input_tile(
  %in, %dst, in_off, ow, iw, stride_h, stride_w,
  dil_h, dil_w, nc, fh, fw, nwin, ...) : ...
几何信息显式携带：sconv.pack_geom 记录 [Ow, Iw, strideH, strideW, dilH, dilW]，避免从 affine map 反推。
管线 03.5

并行 lowering 的 IR 前后对照

并行不是运行时偷偷开线程：sconv-parallelize 把窗口 tile 循环显式改成 scf.parallel。

标记前：串行循环MLIR
scf.for %f = 0 to 192 step 192      // filter tile
  scf.for %w = 0 to 1600 step 160   // 窗口 tile
    %a = ... pack_input_tile ...    // 写共享 scratch
    func.call @sgemm_blas_kernel(...)
标记后：scf.parallel + 私有槽MLIR
scf.for %f = 0 to 192 step 192
  scf.parallel (%w) = 0 to 1600 step 160 {
    %tid = func.call @omp_get_thread_num()
    %slot = memref.reinterpret_cast ... offset: %tid * slotElems
    %a = ... pack_input_tile ...    // 写 tid 自己的槽
    func.call @sgemm_blas_kernel(...)
  }
为什么只有这一层能并行：上层的 %f 循环体内含 filter 打包 （写共享 scratch），再上层是 Nc 归约维。并行链的边界就是「写不相交 + body 是完整工作项」。
